# Bug 4 评估：Electron BrowserWindow reparent 后壁纸不可见

> **状态**：🔴 阻塞中。Bug 1-3 已修（f1c1e5c），但 Bug 4 在十几轮 Windows 真机
> 实测后确认**超出代码层面能修复的范围**。本文档记录全部试错履历、诊断数据、
> 关键洞察，供在 Mac 上分析解决方案时参考。
>
> **环境**：Windows 11 22H2 (Build 22621) + Electron 43.0.0 + koffi 3.1.0
> **日期**：2026-07-04
> **分支**：`desktop/dynamic-layer-v1`

---

## 一、一句话结论

**渲染器完全正常**（禁用 embed 时三联画作为普通窗口正常显示），但
**SetParent 把 BrowserWindow reparent 到跨进程的 WorkerW 后，渲染内容丢失**
（窗口显示原生灰色背景，或视觉上完全不可见）。这是 Electron 43 的 Chromium
在窗口 surface 管理上的行为变化导致的，**不是参数/标志/时序能解决的**。

---

## 二、确定有效的工作（不白费）

### Bug 1-3 已修复并提交（commit `f1c1e5c`）

| Bug | 根因 | 修复 |
|---|---|---|
| 1. 加载即崩 | `koffi.out(koffi.array(...))` 在 koffi 3.x 抛 TypeError | 改用 `koffi.pointer(koffi.array(...))` |
| 2. 找不到 WorkerW | Win11 下 SHELLDLL_DefView 宿主与壁纸 WorkerW 不再是 Z-order 相邻兄弟 | 加 fallback：枚举可见 WorkerW，按面积选最大 |
| 3. guardian 误判 detached | `GetParent` 对 WS_POPUP 顶层窗口返回 owner(0) 不是 parent | 改用 `GetAncestor(hwnd, GA_PARENT)` |

**修复后效果**：guardian steady state 完全安静，`[guardian] healthy (12 ticks)`
每 ~3s 一行，无 re-embed 刷屏。

**这些 Win32 嵌入逻辑无论换什么外壳都适用**——CEF / WebView2 / Tauri 同样需要
reparent 到 WorkerW，guardian / 探测 / 诊断逻辑可以直接复用。

## 三、Bug 4 完整试错履历

### 核心症状

- **禁用 embed**（窗口作为普通顶层窗口）：✅ 三联画正常显示
- **启用 embed**（SetParent 到 WorkerW）：❌ 窗口"闪现一下后消失"
- 进程**没有崩溃**（4 个 electron.exe 持续运行，guardian 一直 healthy）
- 窗口的 Win32 状态**完全正常**：HWND 有效、parent 是 WorkerW、WS_VISIBLE 设置、全屏 rect

→ 结论：**问题精确地在 SetParent 跨进程 reparent**，不是渲染器、不是 guardian、不是崩溃。

### 实验履历（全部在 Windows 真机实测）

| # | 方案 | 依据 | 结果 |
|---|---|---|---|
| 1 | 移除 `disableHardwareAcceleration()` | 调研说 GPU 开 → 不带 NOREDIR | ❌ NOREDIR 仍在，不可见 |
| 2 | `transparent: true` | 两个参考项目都用了它 | ❌ NOREDIR 仍在，不可见 |
| 3 | SetParent 后 `SWP_FRAMECHANGED` | electron-desktop-frame 的反灰窗口技巧 | ❌ 不可见 |
| 4 | `SetWindowLongW` 清除 NOREDIR bit | 直接尝试 | ❌ bit 写进去被立即覆盖（`0x8200100 → 0x8200100`） |
| 5 | 拆分 FRAMECHANGED 与 Z-order 调用 | 避免 Z-order 干扰 surface 绑定 | ❌ 不可见 |
| 6 | `wParam=0xD, lParam=0x1` + 纯 SetParent（无额外 SetWindowPos）| 严格复现 electron-as-wallpaper attach.rs | ❌ 标准探测成功（不再 fallback），但视觉仍不可见 |

### 关键诊断数据

**壁纸窗口的 Win32 状态（reparent 后，视觉不可见时）**：
```
Wallpaper Electron window:
  parent (GetAncestor GA_PARENT) = 133568 (WorkerW)   ← 正确
  IsWindowVisible = 1                                   ← 可见标志在
  rect = 0,0 1726x1029                                  ← 全屏
  GWL_STYLE = 0x14c00000 (WS_VISIBLE=true, WS_CHILD=false, WS_POPUP=false)
  GWL_EXSTYLE = 0x8200100
    WS_EX_NOREDIRECTIONBITMAP = TRUE                    ← ← 嫌疑点
```

**对照：同 WorkerW 下的 SHELLDLL_DefView（图标，正常显示）**：
```
  GWL_EXSTYLE = 0x0  WS_EX_NOREDIRECTIONBITMAP = FALSE   ← 它没有这个标志
```

**同进程其他 Electron 窗口（DevTools 等）**：
```
  大多数 EX = 0x100  WS_EX_NOREDIRECTIONBITMAP = FALSE
  只有 reparent 到 WorkerW 的那个壁纸窗口 EX = 0x8200100 (NOREDIR=true)
```

### Z-order 验证（排除 Z-order 因素）

壁纸窗口在 WorkerW 133568 的子窗口 Z-order 中，位于 SHELLDLL_DefView
**下方第 1 步**——即图标在上、壁纸在下。**Z-order 完全正确，不是被遮挡。**

## 四、关于 `WS_EX_NOREDIRECTIONBITMAP` 的最终判断

### 它是什么

Microsoft 文档：窗口不渲染到重定向表面（redirection surface），用于"没有可见内容
或用表面以外机制提供视觉"的窗口。它控制的是 **OS 在 CreateWindowEx 时是否分配
HWND 支持位图**，是 creation-time 属性。

### 为什么怀疑它

- 壁纸窗口有它，图标窗口没有 → 对照鲜明
- 调研（Agent）引用 Microsoft 文档 + Windows Terminal 源码：**此标志 creation-time
  only，事后 SetWindowLongPtr 无法清除**（实测确认：写进去被立即覆盖）

### 但它可能不是直接原因

有一个矛盾没解决：**NOREDIR 窗口作为顶层窗口时能正常渲染**（禁 embed 时三联画
正常显示）。如果 NOREDIR 直接导致"不渲染"，顶层状态也该看不见。

更准确的因果可能是：**NOREDIR 窗口用独立 composition surface，reparent 到跨进程
父窗口后，这个 surface 失去了合成目标**。Electron 43 的 Chromium 给 BrowserWindow
加 NOREDIR（无论 GPU 开关、transparent 设置），导致跨进程 reparent 必然失败。

### 无法去除的验证

```js
const exBefore = GetWindowLongW(hwnd, GWL_EXSTYLE);  // 0x8200100
SetWindowLongW(hwnd, GWL_EXSTYLE, exBefore & ~0x00200000);
const exAfter = GetWindowLongW(hwnd, GWL_EXSTYLE);   // 0x8200100 ← 没变！
// Chromium 的窗口拒绝了这个样式修改，或写进去被立即覆盖
```

  // fallback: FindWindowExA(progman, 0, "WorkerW", null)

## 六、根本性结论

### Electron 43 + Win11 的失效机制

```
Chromium (Electron 43) 创建 BrowserWindow
  → 带 WS_EX_NOREDIRECTIONBITMAP（独立 composition surface）
  → 作为顶层窗口：surface 绑定到自己的 HWND，正常渲染 ✅
  → SetParent 到 WorkerW（跨进程，explorer.exe 的窗口）
  → 独立 surface 失去跨进程合成目标
  → 渲染内容不到达屏幕，显示原生灰色背景 ❌
```

### 为什么 2021 年的技术在 2025/2026 失效

- `electron-as-wallpaper` 在 2021 年（Electron 14 时代）工作
- Chromium 这 4 年大幅重构了 Windows 窗口 surface 管理
- Electron 43 的 BrowserWindow 默认带 NOREDIR，且**无法通过任何 Electron API、
  窗口选项、或 Win32 SetWindowLongPtr 去除**
- 这不是我们的代码问题，是 Chromium 上游的行为变化

### 这不是机器问题

- Win11 22H2 (Build 22621)，标准版本
- 静态壁纸（BackgroundType=0x0），桌面机制正常
- 系统里 20 个 WorkerW 可能是多次 dev 启动发 `0x052C` 累积的残留（不影响判断）

## 七、待探索的解决方案（供 Mac 上分析）

### 方向 A：换外壳（P1.4 设的止损点）

| 方案 | 优势 | 劣势 |
|---|---|---|
| **CEF (CefSharp)** | Lively 用的方案，内部 widget 容忍 reparent | C++ 工具链，集成成本高 |
| **Tauri + WebView2** | 轻量，Rust 后端，WebView2 窗口行为可能可控 | 需重写外壳，core 包可复用 |
| **纯 WebView2** | 微软原生，Win11 自带，窗口控制权最大 | 仅 Windows，macOS 需另外方案 |

**core 包、IPC 架构、React renderer 全部可复用**——换的只是外壳进程。
Bug 1-3 的 Win32 嵌入逻辑（guardian/探测/诊断）也适用。

### 方向 B：不 reparent，用其他方式画壁纸

- **直接绘制到 WorkerW 的 DC**：用 `GetDCEx` + `BitBlt` 把渲染内容画到 WorkerW
  上，不 reparent BrowserWindow。但这样失去 React/HTML 的动态能力。
- **窗口留在顶层，用区域裁剪模拟壁纸层**：监听桌面焦点，Z-order 调度。
  hacky，不稳定。

### 方向 C：降级 Electron 版本

- 测试 Electron 14-20（2021-2022 年代）是否能工作
- 如果能，证明是版本回归，但长期不推荐用旧版

### 方向 D（未验证，值得一试）

- **Electron 的 `BrowserView` vs `BrowserWindow`**：BrowserView 是嵌入在窗口内的
  视图，可能 surface 行为不同。但 BrowserView 在 Electron 30+ 已废弃。
- **`baseURLForGuest` + `<webview>` 标签**：webview 的渲染路径可能不同
- **直接操作 Chromium 的 `accelerated_widget`**：太底层，不现实

### 我的倾向

**方向 A（换外壳）**，首选 **Tauri + WebView2**：
1. WebView2 是 Edge/Chromium 内核，渲染能力等同
2. WebView2 的窗口由我们完全控制（不是 Electron 包装的 BrowserWindow），
   可能不带 NOREDIR，或允许我们控制 surface 创建
3. Rust 后端 + 现有 core 包（也是 TS，可适配）
4. Tauri 生态成熟，包体小

但这是需要在 Mac 上**先做可行性验证**的——特别是 WebView2 的窗口是否也带
NOREDIR、是否容忍跨进程 reparent。这个无法在 Mac 上实测（要 Windows），
但可以**读 WebView2 文档 + Tauri 源码分析**。

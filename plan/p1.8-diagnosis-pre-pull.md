## 三、🚨 重大发现 2：`GetClassNameW` 的 koffi 声明可能让 guardian 每 tick 误判 detached

### 3.1 问题代码

`user32.ts:224-228`（P1.8 提交版本）：
```ts
const GetClassNameW = user32.func("__stdcall", "GetClassNameW", "int", [
  "int64",
  koffi.out(koffi.array("uint16", 256)),   // ← 提交版
  "int",
]);
```

未提交本地改动把它改成了：
```ts
  koffi.pointer(koffi.array("uint16", 256)),  // ← 未提交版
```

### 3.2 koffi 官方文档怎么说（已读 `node_modules/.pnpm/koffi@3.1.0/.../doc/`）

`pointers.md` 原文：
> By default, just like for objects, array arguments are **copied from JS to C
> but not vice-versa**. You can however change the direction as documented in
> the section on output parameters.

`output.md` 给的 `GetWindowText` 官方范例（与 `GetClassNameW` 同型）：
```js
const GetWindowText = user32.func(
  'int __stdcall GetWindowTextA(HWND hWnd, _Out_ uint8_t *lpString, int nMaxCount)'
);
let buf = Buffer.allocUnsafe(1024);
let length = GetWindowText(hwnd, buf, buf.length);
// ↑ koffi 因为 _Out_ 标记，把 native 写回 buf
```

### 3.3 三种声明的语义对照

| 声明 | koffi 行为 | 调用者 buf 是否被填 | getClassName 返回 |
|---|---|---|---|
| `koffi.array("uint16", 256)` | 默认 JS→C 拷贝 | ❌ 不回写 | `""`（始终） |
| `koffi.out(koffi.array(...))` **（提交版）** | `out()` 文档说作用于 **struct/union/opaque 指针**，回写到新 JS 对象；用于 array 类型时行为不明确，类型系统接受但不是文档支持的用法 | ⚠️ 不确定，文档未覆盖 | 不确定 |
| `koffi.pointer(koffi.array(...))` **（未提交版）** | 指向数组的指针，**默认仍是 JS→C 拷贝**（pointers.md 原文），除非外加 `_Out_` | ❌ 默认不回写 | `""`（很可能） |
| `_Out_ uint16_t *` **（文档范例型）** | primitive 指针 + `_Out_` 限定符，回写到调用者 buf | ✅ 回写 | 正确类名 |

### 3.4 后果（这是关键）

`inspectWindowState()` 算：
```ts
const parentIsWorkerW = parentHwnd !== 0 && getClassName(parentHwnd) === "WorkerW";
```

如果 `getClassName` 始终返回 `""`：
- `parentIsWorkerW` **永远 false**
- guardian 每 tick 都判窗口"已脱离 WorkerW"
- → 每 tick 触发 re-embed（P1.8 是 `reEmbedOnly`，P1.7 是 `embedToDesktop`）
- → 持续闪烁，**和 P1.7 报告里"每 5s detached-from-workerw"的现象完全吻合**

**这条线索能解释为什么 P1.7 的日志里 `parentWorkerW=false` 一直在刷** ——
不一定是 Explorer 真的重建了 WorkerW，也可能是 `getClassName` 根本读不到类名，
guardian **误判**为脱离。

### 3.5 我做不到的事（诚实声明）

- 我**无法在本机跑 Win32 FFI**（虽然 shell 是 MINGW64，但跑 Electron + user32.dll
  需要你那边启动桌面环境），所以**不能 100% 断言**提交版/未提交版哪个实际能读到类名。
- koffi 的 `out(array)` 是文档没明确覆盖的灰色地带 —— 类型系统接受（`TypeSpec`
  包含 `IKoffiDirectionMarker`），但运行时是否回写 `Uint16Array` 没有文档保证。
- **这个必须由你在 Windows 上实测**才能定论（见第六节验证步骤）。

## 七、对你那句"先认错"的回应

你说 P1.7 报告给出 `parentHwnd=0` 每 5s 循环。**这个数据本身可能被 GetClassNameW
的 bug 污染了**：如果 `getClassName` 读不到类名，`parentIsWorkerW` 永远 false，
guardian 永远判 detached —— `parentHwnd=0` 可能是真的脱离，也可能是
"GetParent 返回了一个非 0 的 hwnd，但 getClassName 读它读出来是空串"。

不过 P1.7 日志里 `parentHwnd=0`（不是非 0）这一点，**支持真脱离**（GetParent 都返回 0
了，说明窗口确实没有父窗口了）。所以两个原因可能**同时存在**：
- Explorer 真的会重建 WorkerW（你的判断成立）
- GetClassNameW 也可能读不到类名（我的发现，需步骤 A 验证）

两个都修了，才能确保 guardian 既**不被误判触发**（GetClassNameW 修对），
又在真脱离时**快速、不刺激地**重嵌（P1.8）。

## 二、阻塞点：WebView2 Controller 创建失败

### 症状

```
[host] window created + visible; hwnd = 0x32011a
Error: WebView2 error: WindowsError(Error { code: HRESULT(0x80070057), message: "参数错误。" })
```

`0x80070057` = E_INVALIDARG，发生在 `WebViewBuilder::build(&window)` 内部。

### 已排除的因素

- ❌ WS_EX_TRANSPARENT/LAYERED/NOACTIVATE 样式 — 去掉这些样式，同样失败
- ❌ 窗口不可见 — 加 `set_visible(true)`，同样失败
- ❌ `build_as_child` vs `build` — 两者都失败（build_as_child 因 CW_USEDEFAULT+WS_CHILD，build 因嵌套子窗口无有效 surface）

### 根因（高置信度）

**wry 0.55 用传统 `CreateCoreWebView2Controller`**，它在内部：

1. `create_container_hwnd`：在我们的 tao 窗口（本身是 WorkerW 的子窗口）里创建 wry 自己的容器 HWND
2. `create_controller`：调用 `env.CreateCoreWebView2Controller(hwnd, ...)` 把 controller 绑到容器 HWND

传统 Controller 需要窗口提供有效的渲染目标 surface（swap chain 绑定）。
**我们的窗口是 WorkerW → tao window → wry container 的嵌套子窗口**，
深层嵌套让 surface 创建失败。

### Octos 的成功路径（对照）

读 Octos 源码（`src/Core/Core.cpp` + `src/WebView/WebView.cpp`）发现它用了**完全不同的策略**：

```cpp
// 1. 创建顶层 WS_POPUP 窗口（parent = NULL，不是 WorkerW 的子窗口）
HWND hwnd = CreateWindowEx(
    WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE,
    CLASS_NAME, NULL, WS_POPUP | WS_VISIBLE,
    0,0,0,0, NULL, NULL, g_hInstance, data);

// 2. 先 AttachWebViewCompositionController（在顶层窗口上创建 WebView2）
AttachWebViewCompositionController(hwnd, htmlPath);
    // 内部用 CreateCoreWebView2CompositionController + DirectComposition:
    //   g_dcompDevice->CreateTargetForHwnd(hwnd, FALSE, &dcompTarget);
    //   g_dcompDevice->CreateVisual(&dcompVisual);
    //   dcompTarget->SetRoot(dcompVisual.Get());
    //   ctrl->put_RootVisualTarget(dcompVisual.Get());

// 3. 事后 SetParent 到 WorkerW/Progman
SetParent(hwnd, workerw);
SetWindowPos(hwnd, nullptr, 0,0,0,0, SWP_NOACTIVATE | SWP_SHOWWINDOW | SWP_NOMOVE | SWP_NOSIZE);
```

**三个关键差异**：

| 维度 | Octos（成功） | wry 0.55（失败） |
|---|---|---|
| 窗口类型 | 顶层 WS_POPUP（parent=NULL） | WorkerW 的子窗口（with_parent_window） |
| WebView2 API | `CreateCoreWebView2CompositionController` + DirectComposition | `CreateCoreWebView2Controller`（传统 swap chain） |
| SetParent 时机 | WebView2 创建**之后**（事后） | 窗口创建时（with_parent_window） |

**CompositionController 用 DirectComposition 把 webview 内容作为 visual 合成到窗口**，
不依赖窗口的 swap chain surface——这就是为什么它在跨进程 reparent 后能存活。
传统 Controller 绑定 swap chain 到 HWND，嵌套子窗口提供不了有效 surface。

## 三、备选方案（供 Mac 决策）

### 方案 A：试 Octos 路线（顶层窗口 + wry + 事后 SetParent）

去掉 `with_parent_window`，创建顶层 WS_POPUP 窗口，用 wry 的 `build()` 创建 WebView2，
然后事后 SetParent 到 WorkerW。

- **优势**：只用 tao + wry，不碰 COM，改动小
- **风险**：wry 用传统 Controller，swap chain 在事后 SetParent 时可能失效（这正是 Electron 失败的原因）。但 **tao 创建的 WS_POPUP 窗口没有 Electron 的 NOREDIR 包袱**，可能扛得住。**未验证。**
- **验证成本**：~30 分钟改动 + 测试

### 方案 B：绕过 wry，用 webview2-com crate 直接调 COM

不用 wry，用 `webview2-com`（wry 的底层依赖，Rust 绑定 WebView2 COM API）直接：
1. 创建顶层窗口（tao 或 raw win32）
2. `CreateCoreWebView2EnvironmentWithOptions`
3. `CreateCoreWebView2CompositionController` + DirectComposition（复刻 Octos）
4. 事后 SetParent

- **优势**：完全复刻 Octos 的成功路径，最可靠
- **劣势**：要手写 COM 调用 + DirectComposition 绑定，工作量大（~1-2 天）
- `webview2-com` 已在依赖树里（wry 用它），可以直接引用

### 方案 C：fork/patch wry 暴露 CompositionController

给 wry 加 `WebViewBuilder::with_composition_controller()` 选项，用 CompositionController 路径。
长期最干净，但上游 PR 周期长，不适合现在。

### 我的倾向

**先试方案 A**（30 分钟，低成本验证 wry 传统 Controller 能否扛事后 SetParent）。
如果 A 失败（swap chain 失效，窗口变灰/不可见），**转方案 B**（webview2-com 直接 COM）。
B 是确定能成功的路径（Octos 已证明），只是工作量大。

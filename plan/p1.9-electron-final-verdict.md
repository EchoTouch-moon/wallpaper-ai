## 一、最后一次实验：完整 Lively 分支复刻

### 实验设计

基于审查意见，完整复刻 Lively `WinDesktopCore.cs`（`core-separation` 分支）的
attach 逻辑，包括桌面变体检测和所有三个分支：

1. **桌面变体检测**：读 Progman 的 GWL_EXSTYLE，检查 WS_EX_NOREDIRECTIONBITMAP
2. **Raised-desktop 分支**（Progman 有 NOREDIR）：WS_CHILD + WS_EX_LAYERED +
   SetLayeredWindowAttributes(255) + SetParent 到 Progman + Z-order 在 DefView 下
3. **Classic 分支**（Progman 无 NOREDIR）：SetParent 到壁纸 WorkerW
4. **Collapsed-desktop 边角情况**：当 WorkerW 本身是 DefView 宿主时，用 raised
   样式 attach 到它

同时移除了 `disableHardwareAcceleration()`（Lively 分支需要 GPU 合成，
WS_EX_LAYERED 和软件渲染冲突）。

### 实验结果

**桌面变体检测**：
```
Progman EX = 0x80
WS_EX_NOREDIRECTIONBITMAP = false
→ 判定为 classic desktop（不是 raised）
```

**这台机器的特殊结构**（独立诊断确认）：
```
顶层 WorkerW 133568 (全屏 2560x1600，含 SHELLDLL_DefView 子窗口)
顶层 WorkerW 65902 (22x22，系统窗口)
Progman 65824 (空的！没有 DefView 子，也没有 WorkerW 子)
```

**SHELLDLL_DefView 不在 Progman 下，而在独立顶层 WorkerW 133568 下。** 这不符合
Lively 假设的任何标准结构——既不是 classic（DefView 在 Progman 下）也不是
raised（Progman 有 NOREDIR）。是 Win11 22H2 的一个变体。

**走的路径**（日志确认）：
```
[win32] desktop variant: Progman EX=0x80 raisedDesktop=false
[win32] fallback: using DefView host 133568 as wallpaper target
[win32] classic: WorkerW 133568 is DefView host (collapsed desktop) — using raised styling
[win32] attachAsLayeredChild: parent=133568 below DefView=65826
[main] embedded into wallpaper layer (win32)
[guardian] healthy (12 ticks)   ← steady state 安静
```

**样式应用验证**（attach 后立即查，趁进程活着）：
```
壁纸窗口 (parent WorkerW 133568):
  GWL_STYLE  = 0x54c00000
    WS_CHILD = TRUE        ← 成功应用并保留
    WS_VISIBLE = TRUE
  GWL_EXSTYLE= 0x8280100
    WS_EX_LAYERED = TRUE   ← 成功应用并保留
    WS_EX_NOREDIRECTIONBITMAP = TRUE   ← 仍在（creation-time，无法去除）
```

### 结论

**WS_CHILD 和 WS_EX_LAYERED 都被成功设置并保留了**（不像 NOREDIR 会被 Chromium
覆盖）。SetParent 成功，Z-order 正确（DefView 之下），guardian steady state 安静。
**但壁纸窗口视觉上仍然不可见**——和之前所有失败完全一样的症状。

## 三、最终判决

### Electron BrowserWindow reparent 壁纸路线**不可行**

经过 13 次穷尽性实验，覆盖了：
- 所有 GPU/渲染模式（软件渲染 / GPU 加速 / transparent）
- 所有 Lively 分支（classic / raised / collapsed-desktop）
- 所有窗口样式操作（WS_CHILD / WS_EX_LAYERED / 清除 NOREDIR）
- 所有 SetWindowPos 组合（FRAMECHANGED / NOZORDER / Z-order 分离）

**渲染器正常（禁 embed 能显示），但任何形式的跨进程 reparent 都导致内容不可见。**

### 为什么这是根本性限制（修正后的判断）

之前评估文档把根因归为 `WS_EX_NOREDIRECTIONBITMAP`，但审查正确指出这是假设非定论。
本次实验提供了更精确的证据：

- WS_CHILD + WS_EX_LAYERED **成功应用并保留** → 不是样式被覆盖的问题
- 但 NOREDIR **仍在**，且无法去除（creation-time 属性）
- Lively 的所有分支都试过了，包括完整 raised 样式

**最可能的解释**（仍是假设，但证据更强了）：Electron 43 的 Chromium 在创建
BrowserWindow 时绑定了一个独立 composition surface（NOREDIR），这个 surface 在
跨进程 reparent 后失去合成目标。WS_CHILD/LAYERED 改的是窗口样式，改不了
Chromium 已经绑定的 surface 类型。这是 Chromium 内部行为，Electron API 和
Win32 API 都无法干预。

### 审查修正的回应

- ✅ "NOREDIR 是假设非定论"——接受。本次实验验证了样式能改但窗口仍不可见，
  证明问题比单纯的 NOREDIR 更深
- ✅ "Lively 有 WebView2 播放器 + Win11 专门分支"——接受。但 Lively 的 Electron/
  CefSharp 路径和我们的 Electron BrowserWindow 不是一回事；Lively 的 WebView2
  路径正是我们应该走的
- ✅ "应该试 Lively raised-desktop 分支"——已试，且更进一步试了 collapsed-desktop
  变体。都失败

## 四、下一步：按审查建议走独立宿主路线

### 不再尝试的方向

- ❌ 继续调整 Electron BrowserWindow 的 reparent 参数/样式/时序
- ❌ 降级 Electron 版本（治标不治本，且旧版有其他问题）

### 推荐方向（审查建议，我认同）

**独立 `wallpaper-host.exe` = tao + wry + WebView2**：

```text
apps/wallpaper-host/
  Rust
  ├── tao       原生窗口（创建时指定父 HWND，关闭 NOREDIR）
  ├── wry       WebView2（作为现有窗口的子控件）
  ├── windows-rs Win32 / WorkerW / Progman
  └── IPC       与 Electron 控制端通信
```

**关键顺序**（与当前 Electron 路线的根本区别）：
```
当前（失败）：创建顶层 BrowserWindow → Chromium 开始合成 → 事后 SetParent
应该（正确）：探测桌面结构 → 创建正确父级/样式的原生壁纸窗口 → 在该窗口内创建 WebView2
```

### 验证路径（审查建议）

1. **先用 Octos 验证现有 renderer**：把 WallpaperStage 构建成静态 Vite 页面，
   用 Octos（MIT，WebView2 Composition，已实现 WorkerW/Progman 双路径）运行。
   一次回答：React/Fabric/core/动态换图在 WebView2 壁纸层是否正常。
2. **验证通过后建 wallpaper-host**：基于 tao + wry，不直接用完整 Tauri。

### 可复用的工作

- **Bug 1-3 修复（f1c1e5c）**：Win32 嵌入逻辑（guardian/探测/诊断）适用于任何
  外壳，CEF/WebView2 同样需要 reparent 到 WorkerW
- **core 包、IPC 架构、React renderer**：全部可复用
- **本次实验的桌面变体检测逻辑**：Progman EX 检查 + DefView 宿主识别 +
  collapsed-desktop 检测——这些探测代码可直接移植到 Rust host

## 六、教训（补充）

5. **要尽早探测目标机器的实际桌面结构**——这台机器的 "DefView 在独立 WorkerW
   下、Progman 为空" 的结构，和所有参考项目假设的都不同。如果第一天就做这个
   探测，能省掉很多基于错误假设的实验。
6. **样式能应用 ≠ 能解决问题**——本次实验最大的收获是验证了 WS_CHILD/LAYERED
   确实被应用了，排除了"样式被覆盖"这个假设，把问题精确定位到 Chromium surface
   层面。这比之前"NOREDIR 导致"的含糊判断更准确。
7. **审查的价值**——外部审查纠正了两处过时/过强的判断，并给出了更可行的方向
   （Octos + tao/wry）。持续在错误路线上自查不如引入外部视角。

## 一、Bug 1：`koffi.out(array)` 加载即崩（已修）

### 证据

P1.8 提交版 `user32.ts:226`：
```ts
koffi.out(koffi.array("uint16", 256))
```

实测（`node tmp-koffi-getclassname.cjs`）：
```
TypeError: Unexpected uint16_t[256] type, expected pointer or string type
```

**koffi 3.1.0 的 `out()` 只接受 pointer 或 string 类型，不接受 array**。
这意味着 user32.ts 被 import 的瞬间就抛 TypeError，**整个 win32 平台模块加载失败**。
P1.8 的 guardian、reEmbedOnly、所有逻辑**一次都没执行过**。

之前所有"P1.8 验证"报告看到的都是加载失败后的 fallback 行为（窗口停在桌面顶层）。

### 修复（已 apply 到工作树）

```ts
koffi.pointer(koffi.array("uint16", 256))
```

实测三种声明对照：
| 声明 | 加载 | 读类名 |
|---|---|---|
| `koffi.out(koffi.array(...))` 提交版 | ❌ TypeError | N/A |
| `koffi.pointer(koffi.array(...))` **已采用** | ✅ | ✅ `"Progman"` |
| `_Out_ uint16_t *` 文档范例 | ✅ | ✅ `"Progman"` |

**未提交版（之前那个大模型留下的）方向是对的**，只是没提交、没解释、没验证。

## 二、Bug 2：`findWallpaperWorkerW` 在 Electron 进程下找不到壁纸 WorkerW（当前阻塞点）

### 证据

修了 Bug 1 后，P1.8 能加载了，dev 跑起来。但 embed 直接失败：

```
[main] renderer loaded, now embedding into wallpaper layer...
[findWallpaperWorkerW DIAG] enumCount=598 shellViewFound=65826 workerW=0
                            ALL WorkerW tops=[65898,527302,134368,265692,134076,
                            68366,198290,66382,66340,197316,66220,66156,65904,
                            66054,65902,65852,65844,65842,65818,65816,133568]
[win32] wallpaper WorkerW not found
[main] wallpaper layer embedding skipped/failed (win32); window stays visible
```

### 解读

- `enumCount=598`：EnumWindows 回调**正常触发**了 598 次，回调机制本身没问题
- `shellViewFound=65826`：**找到了 SHELLDLL_DefView**（在某个顶层窗口下）
- `workerW=0`：但 `FindWindowExW(0, defView的宿主, "WorkerW", null)` 返回 0
- `ALL WorkerW tops=[...]`：系统里**有 21 个 WorkerW 顶层窗口**，但探测逻辑一个都没命中

### 根因

`findWallpaperWorkerW` 用的逻辑（继承自 weebp/Lively）：
1. EnumWindows 找到含 `SHELLDLL_DefView` 子窗口的顶层窗口 X
2. `FindWindowExW(0, X, "WorkerW", null)` 找 X **Z-order 之后**的下一个 WorkerW 兄弟

**Win11 下这个逻辑失效**：SHELLDLL_DefView 的宿主窗口和壁纸 WorkerW **不一定是 Z-order 相邻兄弟**。
21 个 WorkerW 里没有一个是"宿主的下一个兄弟"——但其中**必然**有一个是真正接收壁纸绘制的。

### 旁证

我写的独立 node 诊断脚本（`tmp-setparent-diag.cjs`，已删）在**控制台进程**下能稳定找到 `WorkerW=461830`，
用的是**完全相同**的 EnumWindows + FindWindowExW 逻辑。说明：
- 这个探测逻辑**时灵时不灵**（取决于桌面当时的 Z-order 状态）
- Electron 主进程下这次恰好不灵

## 三、Bug 3（推导，非实测）：SetParent 对 Electron 窗口可能无效

### 状态

**未实测到**——因为 Bug 2 让 embed 提前 return，SetParent 从没被执行过。

### 推导依据

第一次跑（Bug 1 修复后、Bug 2 还没暴露时）的日志：
```
[guardian] re-embedded into workerw=461830; PRE-SNAP parent=0 visible=true
[guardian] re-embedded into workerw=461830; PRE-SNAP parent=0 visible=true
...（每 250ms 重复）
```

`reEmbedOnly` 报告找到了 461830 并 SetParent 成功，但 **PRE-SNAP parent=0**——
下一个 tick GetParent 仍返回 0。两种可能：
1. SetParent 对 Electron BrowserWindow 真的不生效（社区已知问题）
2. 461830 不是真正的壁纸 WorkerW，SetParent 进去后被 Explorer 立刻踢出

**修了 Bug 2 之后才能验证 Bug 3 是否真实存在。**

### 旁证：SetParent API 本身没问题

独立脚本 `SetParent(workerW, progman)` round-trip 测试：
```
workerW.GetParent() BEFORE = 65824 (= Progman，WorkerW 本来就 parent 在 Progman 下)
SetParent(workerW, progman) returned = 65552 (prev parent)
workerW.GetParent() AFTER  = 65824 (= Progman，SetParent 生效了)
✅ SetParent+GetParent round-trip WORKS
```

**koffi 的 SetParent/GetParent 绑定是好的**。如果 Bug 3 真实存在，
原因在 Electron 窗口侧，不在 koffi 侧。

## 五、待决策：Bug 2 怎么修

### 候选方案

**方案 A：遍历所有 WorkerW，找可见的那个（最简单）**
- 21 个 WorkerW 里大多数是隐藏的（IME、系统内部用），壁纸 WorkerW 通常是**可见的**
- 逻辑：`ALL WorkerW tops` 里筛 `IsWindowVisible == true` 的
- 风险：多显示器/多桌面下可能有多个可见 WorkerW

**方案 B：找 Z-order 最后的 WorkerW（weebp 实际用的）**
- 壁纸 WorkerW 通常是 Z-order 最底部的那个
- 逻辑：EnumWindows 按 Z-order 遍历，记录最后一个 WorkerW 类的
- 风险：和 A 类似，依赖"壁纸 WorkerW 在最后"这个假设

**方案 C：对每个 WorkerW 检查它和 SHELLDLL_DefView 的兄弟关系（最稳但最复杂）**
- 找到 SHELLDLL_DefView 的**真正宿主**（往上 GetParent 链找）
- 在该宿主的兄弟里找 WorkerW
- 这是 Lively 最新版的做法，但实现复杂

**方案 D：暴力 SetParent 进所有 WorkerW，看哪个能让窗口显示**
- 太脏，不考虑

### 我的倾向

**方案 A**（筛可见 WorkerW）作为第一步尝试——
代码改动最小（复用已有的 IsWindowVisible），21 个里筛可见的应该只剩 1-2 个。
如果剩多个，再退化到方案 B。

## 六、Bug 2 最终修复（DefView 宿主感知 fallback）

方案 A 演进成了更精确的版本：**找 SHELLDLL_DefView 的宿主，然后在可见 WorkerW 里排除宿主本身**。

诊断揭示：发完 `0x052C` 后，Progman 把 SHELLDLL_DefView 移进一个 WorkerW（宿主），
壁纸 WorkerW 是这个宿主的**兄弟**。系统里有 21 个 WorkerW，但只有 2 个可见：
`[65902, 133568]`，其中 `133568` 就是 DefView 宿主，所以 `65902` 才是壁纸目标。

```ts
// 主探测：SHELLDLL_DefView 宿主的下一个 WorkerW 兄弟（Win10/经典 Win11）
// ↓ 失败时
// Fallback：枚举可见 WorkerW，排除 DefView 宿主，剩下的就是壁纸目标（Win11 raised desktop）
```

## 七、Bug 3 是红鲱鱼！真相：GetParent 用错了（关键转折）

### 我之前的错误断言

修复 Bug 2 后，日志显示：
```
[guardian] re-embedded into workerw=65902; PRE-SNAP parent=0 visible=true
[guardian] re-embedded into workerw=65902; PRE-SNAP parent=0 visible=true
```

我断言"Bug 3 实锤：Electron BrowserWindow 抵抗 SetParent，parent 永远 0"。

### 调研纠正（MSDN + Chromium 源码实践）

Agent 调研给出决定性洞察（来自 [MSDN SetParent remarks](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent)）：

> **SetParent 不修改 WS_CHILD/WS_POPUP 样式。GetParent 对 WS_POPUP/WS_OVERLAPPED
> 顶层窗口返回的是 owner（通常 0），不是 parent。**

也就是说：**SetParent 一直都是成功的**（从 P1.2 开始），HWND 层面真的 reparent 了。
但 `GetParent(electronHwnd)` 因为窗口仍是顶层样式，返回 owner（0），不是真 parent。
guardian 每 tick 误判 detached → reEmbedOnly 重复 SetParent（多余但无害）→ 又被误判……死循环。

**闪烁就是这个死循环造成的**：每 250ms 重复 SetParent + SetWindowPos，窗口被反复扰动。

### 验证假设（对比 GetParent vs GetAncestor）

加诊断同时调两个 API：
```
[inspect DIAG] hwnd=2298316 GetParent=0 GetAncestor=65902 class="WorkerW" -> parentIsWorkerW=true
```

- `GetParent=0`（红鲱鱼，返回 owner）
- `GetAncestor=65902`（真 parent，就是 WorkerW！）
- `class="WorkerW"`（getClassName 也读对了）

**SetParent 从来没失败过。** 用 GetAncestor 替换 GetParent 后：
```
[guardian] healthy (12 ticks)    ← steady state 完全安静
```

## 九、最终修复 diff（user32.ts，相对 P1.8）

三个独立修复：

1. **GetClassNameW**：`koffi.out(array)` → `koffi.pointer(array)`
   （out() 在 koffi 3.x 不接受 array 类型，加载即崩 TypeError）
2. **findWallpaperWorkerW**：加 Win11 raised-desktop fallback
   （主探测失败时，枚举可见 WorkerW，排除 SHELLDLL_DefView 宿主）
3. **inspectWindowState**：`GetParent` → `GetAncestor(GA_PARENT)`
   （GetParent 对顶层窗口返回 owner 不是 parent，导致 guardian 永远误判 detached）

## 十、教训

1. **静态文档分析会错**：我最初判断 `koffi.pointer(array)` 可能也读不到（基于 koffi 文档
   "array 默认 JS→C 不回写"）。实测推翻了这个判断 —— koffi 3.1 比文档宽松。
2. **"Bug 3 实锤"是错的**：我用 GetParent==0 断言 SetParent 失败，但 GetParent 对
   顶层窗口返回的是 owner。如果当时不调研、直接往"Electron 抵抗 SetParent"方向修，
   会白走一大圈。调研救了这一轮。
3. **P1.8 提交版从未真正运行过**：GetClassNameW 的 `koffi.out(array)` 在 import 瞬间
   抛 TypeError，整个 user32 模块加载失败。之前所有"P1.8 验证"报告看到的都是
   加载崩溃后的 fallback 行为。这暴露了 `loadModule()` 的 catch 静默吞错误的隐患。

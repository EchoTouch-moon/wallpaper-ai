## 六、根因分析（按概率排序）

### 假设 A：`setBounds` 尺寸微调触发窗口隐藏

| 项目 | 详情 |
|---|---|
| **位置** | `main/index.ts` 第 140-143 行 |
| **代码** | `window.setBounds({ width: w + 1 })` → `setBounds({ width: w })` |
| **机制** | 在 WorkerW 内的 `SetParent` 后微调尺寸，可能触发 DWM/Shell 的布局刷新，将窗口推到 WorkerW 背景控件后面或设置 `WS_VISIBLE` 为 false |
| **验证方法** | 注释掉 setBounds 调用，只保留 `invalidate()` |

### 假设 B：`SWP_NOACTIVATE` 导致窗口被最小化/隐藏

| 项目 | 详情 |
|---|---|
| **位置** | `user32.ts` 第 174-182 行、第 192-200 行 |
| **代码** | `SetWindowPos(hwnd, HWND_BOTTOM, ..., SWP_NOACTIVATE)` |
| **机制** | `SWP_NOACTIVATE` (0x0010) 禁止激活窗口，在某些 Windows 版本/DWM 配置下，结合 `HWND_BOTTOM` 可能触发窗口自动最小化或隐藏 |
| **验证方法** | 移除 `SWP_NOACTIVATE` flag，或改为 `SWP_NOMOVE \| SWP_NOSIZE` |

### 假设 C：WorkerW 被 Explorer 重建

| 项目 | 详情 |
|---|---|
| **位置** | Windows Shell 行为 |
| **机制** | `0x052C` 消息触发的 WorkerW 是临时的，Explorer 可能在检测到无子窗口后销毁它，或桌面刷新时重建 |
| **验证方法** | 在 embed 后加轮询检查 `workerW` 句柄是否仍然有效 |

### 假设 D：`disableHardwareAcceleration` 本身导致问题

| 项目 | 详情 |
|---|---|
| **位置** | `main/index.ts` 第 163 行 |
| **机制** | 软件渲染在某些 GPU 驱动下可能有兼容性问题，或需要额外的初始化时间 |
| **验证方法** | 移除该调用，恢复到 GPU 渲染 |

## 九、结论

P1.4 的 `disableHardwareAcceleration` **解决了渲染管线问题**（证明三联画能渲染），但引入了**窗口生命周期问题**（渲染后立即消失）。最可能的原因是 `setBounds` 微调触发了 DWM 的不可见状态变更，或 `SWP_NOACTIVATE` 在某些条件下导致窗口被最小化。下一步需要隔离这两个变量。

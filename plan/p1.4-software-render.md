## 真正的根因（终于看清了）

P1.3 报告里有三个互相矛盾的事实，组合起来锁定根因：

| 事实 | 含义 |
|---|---|
| 控制台打印 `renderer loaded` | HTML 被成功解析 |
| 品红背景（内联 CSS）没出现 | 内联 `<style>` 在 HTML 解析时就生效，**不依赖 JS** |
| 显示灰色 | 不是品红、不是白色（Electron 默认）、是窗口原生背景 |

**结论**：Chromium 的画面**根本没到屏幕**。我们看到的灰色是 Win32 窗口的原生背景画刷。

## 机制解释

Chromium 用 **GPU 合成（Direct3D/ANGLE）** 渲染网页。GPU swap chain 绑定在窗口的 HWND 和它在窗口树里的位置。`SetParent` 把 BrowserWindow reparent 到 WorkerW（属于 explorer.exe）时：

- swap chain 失效
- Chromium **不知道**要重建它
- 网页内容停止呈现
- 只剩窗口原生灰色背景

**这正是 Lively Wallpaper 不用 Electron、而用 CefSharp 并抽取内部 `Chrome_WidgetWin_0` 子窗口去 reparent 的原因**——CEF 的内部 widget 容忍 reparent，浏览器顶层窗口不容忍。

## 核心修复：`app.disableHardwareAcceleration()`

Chromium 有专门为嵌入式/kiosk/reparent 场景设计的开关：强制 CPU 软件渲染，**不用 GPU swap chain**，所以 reparent 不破坏呈现。

```ts
// 必须在 app.whenReady() 之前调用
app.disableHardwareAcceleration();
```

这一行**直接验证根因**。如果它生效，我们不需要换栈——很多生产级 kiosk/数字标牌 Electron 应用就是这么跑的，静态壁纸的性能完全够。

## 关于"要不要换栈"的判断

**现在换为时过早，但需要设止损点：**

- ✅ 如果 P1.4（软件渲染）生效 → Electron 路线确认，继续
- ❌ 如果 P1.4 仍不生效 → 认真评估 CEF（CefSharp）/ Tauri WebView2 方案，不再在 Electron 里硬钻

P0 抽的 core 包、IPC 架构、wallpaper renderer（React）**全部可复用**——换的只是外壳进程（Electron → CEF）。所以即使最坏情况，沉没成本也很小。

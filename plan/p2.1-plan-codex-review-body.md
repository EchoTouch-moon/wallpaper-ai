## API 调研结论（已读源码确认）

- tao 0.35.3：`EventLoopBuilder::<T>::with_user_event().build()` + `EventLoopProxy::send_event` + `Event::UserEvent(T)` 全可用；回调第二参数是 `&EventLoopWindowTarget<T>`，`WindowBuilder::build(event_loop)` 在回调内可直接创建窗口（`examples/reopen_event.rs` 的 `Option<Window>` + `window = None` + `Window::new(event_loop)` 模式）。`WindowId: PartialEq + Eq + Hash + Copy + Clone`，可用于旧窗口事件过滤。

## 架构：HostRuntime 状态机

```
struct HostRuntime {
    generation: u64,
    window: Window,
    webview: WebView,
    target: DesktopTarget,
    window_id: WindowId,
    page_ready: bool,
}

enum RecoveryState {
    Running,
    Recovering { next_attempt_at: Instant, attempt: u32 },
}

struct HostState {
    runtime: Option<HostRuntime>,
    recovery: RecoveryState,
    reparent_at: Option<Instant>,
    next_guardian_at: Instant,
    next_status_at: Instant,
    recovery_token: u64,
}
```

## 恢复流程（事件回调内同步执行）

1. guardian 在 MainEventsCleared 检测到故障（parent 改变 / host IsWindow==false），通过 `EventLoopProxy::send_event(RecoveryRequested)` 投递。**只发一次**：进入 Recovering 后后续 guardian tick 跳过。
2. `Event::UserEvent(RecoveryRequested)` 中执行 `rebuild_host()`：
   - `runtime.take()`；显式先 drop WebView，再 drop Window（顺序固定，留在 UI/COM 线程）；清理路径允许 `IsWindow == false`，不当致命错误
   - `recovery_token += 1`（丢弃在途 page-loaded 回调）
   - `desktop::probe()` 重新探测（0x052C 在 probe 内部按"每恢复周期一次"发送，不重复）
   - 用 `EventLoopWindowTarget` 创建**隐藏** Window（`with_visible(false)`，保留 `with_undecorated_shadow(false)`）
   - `WebViewBuilder::build(&window)`（同步阻塞）
   - 注册 `with_on_page_load_handler`：`Finished` 时校验 recovery_token 匹配 → 置 page_ready=true → `do_reparent` + `set_visible(true)`
   - 成功 → `generation += 1`，RecoveryState = Running，重置 guardian/status deadlines
3. 失败（probe / build / window 任一失败）→ 保留 Recovering，指数退避重试，不退出整个 host。

## 退避

attempt 1→500ms, 2→1s, 3→2s, 4→4s, ≥5→8s（封顶）。成功后清零。

## 关键设计决策（请审核）

1. **首次启动也走状态机**：`HostState` 初始化 `runtime=None, recovery=Recovering{next_attempt_at=now, attempt=0}`，第一次 MainEventsCleared 就触发 `rebuild_host` 创建 generation 0。启动与恢复共用同一段代码，避免两套逻辑。是否认可？

2. **guardian → 重建用 EventLoopProxy 解耦**：guardian 在 MainEventsCleared 只"发现"故障并发 `RecoveryRequested`，重建在 `Event::UserEvent` 里执行。理由：符合你说的"解耦且幂等"。**风险**：在 MainEventsCleared 内调 `send_event` 是从事件循环线程内向同一事件循环投递，应该安全（不跨线程），但我没在 tao 源码里找到明确保证。**回退**：若实机出现重入/死锁，退化为 MainEventsCleared 内直接原地启动恢复（不解耦，状态机仍正确）。这个回退点可接受吗？

3. **page-ready 前不 attach**：build 完成后页面还在加载（NavigationCompleted 未到），attach 推迟到 `PageLoadEvent::Finished`。期间窗口隐藏（`with_visible(false)`），避免显示空白页。generation token 防止恢复风暴下旧 webview 的 Finished 回调 attach 错对象。

4. **首次 reparent 失败的处理**：现有 one-shot `reparent_at` 失败仅 +1s 重试（保留），不直接转 Recovering——首次 reparent 失败多半是 page 还没 ready，真正的 Explorer 重启由 guardian 捕获后走状态机。这个区分合理吗？

5. **窗口事件按 WindowId 过滤**：`Event::WindowEvent { window_id, .. }` 比较 `window_id == runtime.window_id`；旧窗口的 `CloseRequested`/`Destroyed` 等迟到事件忽略，不影响新一代。

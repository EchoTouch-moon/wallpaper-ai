## 决定性诊断数据

reparent 后子窗口的 GetWindowRect（屏幕坐标）：
```
WRY_WEBVIEW          rect=11,2,2560x1600    ← 起点 (11,2) 不是 (0,0)！
Chrome_WidgetWin_0   rect=11,2,2560x1600
Chrome_WidgetWin_1   rect=11,2,2538x1587
Chrome_RenderWidgetHostHWND rect=11,2,2538x1587
Intermediate D3D Window rect=11,2,2560x1600
```

**所有子窗口左上角都在 (11, 2)** — 不是 (0, 0)。

## 根因

host 窗口有 ~11px 的非客户区 insets（边框）：
- `host GetClientRect = 2538x1587`（窗口 outer 2560×1600 减去边框 22×13）
- client area 原点在屏幕坐标 (11, 2)，所以 WRY_WEBVIEW（在 client (0,0)）的屏幕坐标也是 (11, 2)
- 这导致壁纸内容向右下偏移，左边/上边露出原壁纸，右边/下边被裁

### 为什么清了 WS_CAPTION 还有边框

- tao 的 `with_decorations(false)` **在 Windows 上不清除 WS_CAPTION**（实测 `state after create` 的 style 含 WS_CAPTION）
- 我在 reparent 时清了 WS_CAPTION（解决了可见的标题栏"壳子"）
- 但 **DWM 缓存了窗口的 NC insets**，清除 style 后 insets 没自动重算
- 尝试过的修复都没消除 insets：
  - `SWP_FRAMECHANGED` — 没效果
  - `DwmSetWindowAttribute(DWMWA_NCRENDERING_POLICY, DWMNCRP_DISABLED)` — 没效果
  - 在 WebView2 创建前就清 WS_CAPTION + SWP_FRAMECHANGED — 没效果
- Win11 DWM 对所有窗口都维护一个隐藏的 resize border（用于 snap 手势），即使 WS_CAPTION 清除

### DPI 数据

- 系统 DPI = 96（node koffi 查到，但 node 是 System DPI Aware）
- **窗口 DPI = 144（1.5x）** — tao 默认 Per-Monitor V2，host 窗口在 1.5x 显示器上
- 物理屏幕 2560×1600，逻辑 1707×1067
- `SM_CXSIZEFRAME=4` + `SM_CXPADDEDBORDER=4` = 8px 物理边框，DPI 1.5x 后 = **12px ≈ 观测的 11px**

## 待实施的修复方向

### 方向 A：subclass WM_NCCALCSIZE（最可靠）

用 `SetWindowSubclass`（comctl32，已在 `Win32_UI_Shell` feature）给 host 窗口打补丁，
拦截 `WM_NCCALCSIZE` 当 `wParam==TRUE` 时返回 0 — 告诉 Windows "整个窗口 rect 都是 client area"。

```rust
// 伪代码
unsafe extern "system" fn nc_subclass(
    hwnd: HWND, msg: u32, wparam: WPARAM, lparam: LPARAM,
    _id: usize, _ref: usize,
) -> LRESULT {
    if msg == WM_NCCALCSIZE && wparam.0 != 0 {
        return LRESULT(0); // 整个窗口 = client area，无 NC insets
    }
    DefSubclassProc(hwnd, msg, wparam, lparam)
}
SetWindowSubclass(hwnd, Some(nc_subclass), 1, 0);
```

风险：可能干扰 tao 的事件处理（tao 的窗口过程也处理 WM_NCCALCSIZE）。
需要在 subclass proc 里对非 NCCALCSIZE 消息调 DefSubclassProc 透传给 tao。

### 方向 B：让窗口 outer 大于屏幕（hack）

把窗口设成 2560+22 × 1600+13 = 2582×1613，让 client area 正好 = 2560×1600。
简单但脏——窗口超出屏幕，可能影响多显示器。

### 方向 C：用 CompositionController（绕过传统 Controller 的 NC 限制）

Octos 用 CompositionController + DirectComposition，不依赖窗口的 client area。
但需要绕过 wry 直接调 COM，工作量大。

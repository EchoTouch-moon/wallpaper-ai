> ## 二、Lifecycle 至少要有 Queued / WaitingForPage / Running / Backoff
>
> 建议改为类似：
>
> ```rust
> enum Lifecycle {
> RecoverQueued { token: u64, attempt: u32, reason: RecoveryReason },
> WaitingForPage { token: u64, attempt: u32, timeout_at: Instant },
> Running,
> Backoff { token: u64, attempt: u32, retry_at: Instant },
> }
> ```
>
> `Building` 可作为 `RecoveryRequested` handler 内的同步临时阶段，不一定落入 enum。
>
> 原因：如果 build 成功后仍维持笼统的 `Recovering { next_attempt_at }`，deadline 到达时可能在
> PageLoadEvent::Finished 之前再次 rebuild，主动丢掉刚创建的候选；如果停止 retry，又没有
> page-load timeout，则 Finished 永不到时会永久卡死。

> 必须增加 page-ready timeout（建议 10–15s）：超时后 drop 候选 runtime，进入 Backoff。
>
> `HostRuntime.page_ready` 可删除，生命周期 enum 已表达该状态；`window_id` 可保留用于过滤迟到事件。
>
> ## 三、page-load handler 只能投递 HostEvent，不能直接改 HostState/attach
>
> `with_on_page_load_handler` 的闭包是 `'static`，请只捕获 `EventLoopProxy + token`：
>
> ```rust
> HostEvent::PageLoadFinished { token, url }
> ```
>
> 闭包遇到 `PageLoadEvent::Finished` 时 send_event；真正的 token/state/url 校验和
> `do_reparent()` 必须回到 `Event::UserEvent` 中执行。
>
> 处理 PageLoadFinished 时：
> 1. 当前 lifecycle 必须是同 token 的 WaitingForPage；否则视为旧 generation/重复导航事件并忽略。
> 2. URL 必须是预期的 `wallpaper://localhost`（允许你确认后的标准化尾斜杠形式），避免错误页/后续导航触发 attach。

> generation 并转 Running。
> 4. 任一步失败：显式先 drop WebView、再 drop Window，进入 Backoff；不要在同一个可能已部分

> 你第 4 点“不直接转 Recovering”的判断不成立：PageLoadFinished 之后 attach 失败已不是“页面可能没

> ## 五、EventLoopProxy 同线程投递：认可，不设 inline fallback

> UserEvent，没有“只能跨线程”的限制；在 MainEventsCleared 内调用应作为队列投递使用。发送前先把状态置为
> RecoverQueued，保证 guardian 不会重复排队。

> 不建议保留“失败就 MainEventsCleared 内直接 rebuild”的回退，它会制造两条执行路径。若 `send_event`

> > - tao 0.35.3：`EventLoopBuilder::::with_user_event().build()` + `EventLoopProxy::send_event` + `Event::UserEvent(T)` 全可用；回调第二参数是 `&EventLoopWindowTarget`，`WindowBuilder::build(event_loop)` 在回调内可直接创建窗口（`examples/reopen_event.rs` 的 `Option` + `window = None` + `Window::new(event_loop)` 模式）。`WindowId: PartialEq + Eq + Hash + Copy + Clone`，可用于旧窗口事件过滤。
> > - wry 0.55.1：`WebViewBuilder::build(&window)` 是**同步阻塞**的（Windows 走 `webview2_com::wait_with_pump` 内部消息泵等 COM 回调），返回时 `ICoreWebView2Controller` 已就绪——可在事件回调内同步创建。但 build 完成 ≠ page ready，需 `with_on_page_load_handler(PageLoadEvent::Finished)` 检测。`WebView` 不是 `Send`，必须留在事件循环线程持有/销毁。
> >
> > ## 架构：HostRuntime 状态机
> >
> > ```
> > struct HostRuntime {
> > generation: u64,
> > window: Window,
> > webview: WebView,
> > target: DesktopTarget,
> > window_id: WindowId,
> > page_ready: bool,
> > }
> >
> > enum RecoveryState {
> > Running,
> > Recovering { next_attempt_at: Instant, attempt: u32 },
> > }
> >
> > struct HostState {
> > runtime: Option,
> > recovery: RecoveryState,
> > reparent_at: Option,
> > next_guardian_at: Instant,
> > next_status_at: Instant,
> > recovery_token: u64,
> > }
> > ```
> >
> > ## 恢复流程（事件回调内同步执行）
> >
> > 1. guardian 在 MainEventsCleared 检测到故障（parent 改变 / host IsWindow==false），通过 `EventLoopProxy::send_event(RecoveryRequested)` 投递。**只发一次**：进入 Recovering 后后续 guardian tick 跳过。
> > 2. `Event::UserEvent(RecoveryRequested)` 中执行 `rebuild_host()`：
> > - `runtime.take()`；显式先 drop WebView，再 drop Window（顺序固定，留在 UI/COM 线程）；清理路径允许 `IsWindow == false`，不当致命错误
> > - `recovery_token += 1`（丢弃在途 page-loaded 回调）
> > - `desktop::probe()` 重新探测（0x052C 在 probe 内部按"每恢复周期一次"发送，不重复）
> > - 用 `EventLoopWindowTarget` 创建**隐藏** Window（`with_visible(false)`，保留 `with_undecorated_shadow(false)`）
> > - `WebViewBuilder::build(&window)`（同步阻塞）
> > - 注册 `with_on_page_load_handler`：`Finished` 时校验 recovery_token 匹配 → 置 page_ready=true → `do_reparent` + `set_visible(true)`
> > - 成功 → `generation += 1`，RecoveryState = Running，重置 guardian/status deadlines
> > 3. 失败（probe / build / window 任一失败）→ 保留 Recovering，指数退避重试，不退出整个 host。
> >
> > ## 退避
> >
> > attempt 1→500ms, 2→1s, 3→2s, 4→4s, ≥5→8s（封顶）。成功后清零。
> >
> > ## 关键设计决策（请审核）
> >
> > 1. **首次启动也走状态机**：`HostState` 初始化 `runtime=None, recovery=Recovering{next_attempt_at=now, attempt=0}`，第一次 MainEventsCleared 就触发 `rebuild_host` 创建 generation 0。启动与恢复共用同一段代码，避免两套逻辑。是否认可？
> >
> > 2. **guardian → 重建用 EventLoopProxy 解耦**：guardian 在 MainEventsCleared 只"发现"故障并发 `RecoveryRequested`，重建在 `Event::UserEvent` 里执行。理由：符合你说的"解耦且幂等"。**风险**：在 MainEventsCleared 内调 `send_event` 是从事件循环线程内向同一事件循环投递，应该安全（不跨线程），但我没在 tao 源码里找到明确保证。**回退**：若实机出现重入/死锁，退化为 MainEventsCleared 内直接原地启动恢复（不解耦，状态机仍正确）。这个回退点可接受吗？
> >
> > 3. **page-ready 前不 attach**：build 完成后页面还在加载（NavigationCompleted 未到），attach 推迟到 `PageLoadEvent::Finished`。期间窗口隐藏（`with_visible(false)`），避免显示空白页。generation token 防止恢复风暴下旧 webview 的 Finished 回调 attach 错对象。
> >
> > 4. **首次 reparent 失败的处理**：现有 one-shot `reparent_at` 失败仅 +1s 重试（保留），不直接转 Recovering——首次 reparent 失败多半是 page 还没 ready，真正的 Explorer 重启由 guardian 捕获后走状态机。这个区分合理吗？
> >
> > 5. **窗口事件按 WindowId 过滤**：`Event::WindowEvent { window_id, .. }` 比较 `window_id == runtime.window_id`；旧窗口的 `CloseRequested`/`Destroyed` 等迟到事件忽略，不影响新一代。
> >

> > > > > > # WallpaperAI 动态壁纸层 P1 止损 + P2.0 突破报告
> > > > > >
> > > > > > ## 背景
> > > > > >
> > > > > > WallpaperAI 项目的动态壁纸层（在桌面图标下方实时渲染 React 三联画）经历了从
> > > > > > Electron 路线止损到原生 WebView2 宿主突破的完整过程。当前 P2.0 核心架构已验证通过，
> > > > > > 进入视觉打磨阶段。本邮件同步完整进展、关键结论和下一步。
> > > > > >
> > > > > > ## 一、P1（Electron BrowserWindow 路线）止损
> > > > > >
> > > > > > ### 尝试过的方案（共 13 次实验，全部失败）
> > > > > >
> > > > > > Electron BrowserWindow + SetParent reparent 到 WorkerW 的路线，穷尽验证后确认不可行：
> > > > > >
> > > > > > | 维度 | 试过的方案 |
> > > > > > |---|---|
> > > > > > | GPU 模式 | 软件渲染 / GPU 加速 / transparent |
> > > > > > | Lively 分支 | classic / raised / collapsed-desktop |
> > > > > > | 窗口样式 | WS_CHILD / WS_EX_LAYERED / 清除 NOREDIR |
> > > > > > | SetWindowPos | FRAMECHANGED / NOZORDER / Z-order 分离 / 纯 SetParent |
> > > > > > | 0x052C 参数 | wParam=0 / 0xD（Lively/electron-as-wallpaper 同款）|
> > > > > >
> > > > > > ### 对照实验（决定性）
> > > > > >
> > > > > > - 禁用 embed（窗口作为普通顶层）→ ✅ 三联画正常显示
> > > > > > - 启用 embed（任何形式的 SetParent 到 WorkerW）→ ❌ 渲染内容消失（窗口原生灰色背景）
> > > > > >
> > > > > > **结论**：问题 100% 在跨进程 reparent，不是渲染器、不是 guardian、不是崩溃。
> > > > > >
> > > > > > ### 最终根因（修正后）
> > > > > >
> > > > > > 最初归因为 `WS_EX_NOREDIRECTIONBITMAP`，但外部审查正确指出这是"假设非定论"。
> > > > > > 更准确的判断：Electron 43 的 Chromium 在创建 BrowserWindow 时绑定独立 composition surface，
> > > > > > 跨进程 reparent 后该 surface 失去合成目标。这是 Chromium 上游行为，不是代码层面能修的。
> > > > > >
> > > > > > 完整诊断在 `plan/p1.9-electron-final-verdict.md`（commit 7f69dbd）。
> > > > > >
> > > > > > ## 二、Octos ground-truth 验证（PASS）
> > > > > >
> > > > > > 在放弃 Electron 前，用 Octos（MIT，WebView2 Composition + WorkerW/Progman 双路径）
> > > > > > 验证现有 React renderer 能否在 WebView2 壁纸层工作。
> > > > > >
> > > > > > **结果**：✅ PASS。三联画完整显示、位于图标下方、诊断角标正确
> > > > > > （`platform: octos-webview2`、`embedded: true`、`template: triptych_desktop_equal`）、
> > > > > > Explorer 重启后自动恢复、内存稳定无泄漏。
> > > > > >
> > > > > > 这证明：**React renderer + @wallpaper/core + WebView2 完全可行**，问题只在 Electron 的
> > > > > > BrowserWindow。后续应走独立原生宿主（tao + wry + WebView2）。
> > > > > >
> > > > > > ## 三、P2.0 原生 WebView2 宿主（核心突破）
> > > > > >
> > > > > > ### 架构
> > > > > >
> > > > > > ```
> > > > > > apps/wallpaper-host/ (Rust)
> > > > > > ├── tao 原生窗口 + 事件循环
> > > > > > ├── wry WebView2
> > > > > > ├── windows-rs Win32 桌面层探测（WorkerW/Progman）
> > > > > > └── custom protocol 安全加载本地 renderer 静态资源
> > > > > > ```
> > > > > >
> > > > > > 关键顺序（与 Electron 失败路线的根本区别）：
> > > > > > 1. 探测桌面拓扑 → 找到正确的 WorkerW parent
> > > > > > 2. 创建**顶层** tao 窗口（不指定 parent）
> > > > > > 3. 在顶层窗口创建 WebView2（surface 建立）
> > > > > > 4. **事后** SetParent 到 WorkerW
> > > > > >
> > > > > > ### A0/A1/A2 三阶段验证（全过）
> > > > > >
> > > > > > 按外部判决要求，用严格隔离实验确认传统 WebView2 Controller 的真实边界：
> > > > > >
> > > > > > - **A0（top-level）**：纯顶层窗口，无 parent，WebView2 创建前不加任何样式
> > > > > > → ✅ WebView2 创建成功，三联画显示。证明 wry 基线工作。
> > > > > >
> > > > > > - **A1（reparent）**：WebView2 创建后 SetParent 到 WorkerW
> > > > > > → ✅ 三联画在壁纸层（图标下方）持续显示，2+ 分钟稳定。
> > > > > > **这推翻了"嵌套子窗口无 surface"假设**——传统 Controller 能在事后 SetParent 存活。
> > > > > >
> > > > > > - **A2（reparent-click-through）**：加 WS_EX_TRANSPARENT
> > > > > > → ✅ 图标点击/框选/右键全正常，Win+D 正常，不抢焦点，Alt+Tab/任务栏不出现。
> > > > > >
> > > > > > **核心结论**：传统 WebView2 Controller（不需要 CompositionController + DirectComposition）
> > > > > > 完全能用于壁纸层。失败的是 Electron BrowserWindow 的特定实现，不是技术路线本身。
> > > > > >
> > > > > > ### 桌面探测（实测正确）
> > > > > >
> > > > > > Win11 22H2 上命中 Classic 分支：0x052C 成功创建独立全屏 WorkerW（area=1821369），
> > > > > > 正确排除 22×22 系统 WorkerW。代码在 `apps/wallpaper-host/src/desktop.rs`，
> > > > > > 支持 Classic / Raised / Collapsed 三种变体。
> > > > > >
> > > > > > ## 四、当前残留问题（视觉打磨，非阻塞）
